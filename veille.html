Veille informatique : l'écosystème .NET

Je travaille tous les jours avec .NET, la plateforme de développement de Microsoft. Je suis son évolution pour comprendre les choix techniques de mes projets et anticiper ceux qui viendront. Sur cette page, je partage ce que j'apprends, en partant de situations rencontrées en alternance.

Ma méthode

  • Des vidéos, avant tout : je me tiens informé principalement par des vidéos YouTube de développeurs qui présentent les nouveautés, comparent des approches ou racontent leurs retours d'expérience. C'est un format qui me permet de voir le code fonctionner, pas seulement de le lire.
  • La pratique en alternance : je relie chaque sujet à une situation concrète de mes projets. Une notion ne devient vraiment claire pour moi que lorsque je l'ai rencontrée dans le code de SpoolBox ou de Sirene.
  • Le partage sur cette page : écrire un article m'oblige à reformuler ce que j'ai compris, et à vérifier que je sais l'expliquer simplement.

Un même logiciel, trois versions de .NET : pourquoi ?

Novembre 2026 · lié au projet SpoolBox

En travaillant sur SpoolBox, j'ai découvert une solution qui mélange trois « saveurs » de .NET. Ce n'est pas un oubli : c'est une situation courante dans les entreprises qui ont des applications anciennes.

  • .NET 10, la version actuelle avec support long terme (sortie en novembre 2025), pour l'interface WPF, l'API et le traitement de nuit.
  • .NET Standard 2.0 pour la bibliothèque commune. Ce n'est pas une plateforme mais un « contrat » : une bibliothèque qui le respecte peut être utilisée à la fois par du .NET moderne et par l'ancien .NET Framework.
  • .NET Framework 4.8, en 32 bits, pour la génération des PDF. Cette plateforme n'évolue plus, mais certaines bibliothèques anciennes ne fonctionnent qu'avec elle.

Ce que j'en retiens : quand une dépendance bloque la migration, on peut l'isoler dans un programme séparé plutôt que de bloquer toute l'application sur une vieille version. Il faut alors gérer la communication entre les deux et un délai maximal d'exécution, mais le reste du code profite des nouveautés de .NET.

Partager du code entre applications : DLL copiée ou paquet NuGet ?

Novembre 2026 · lié au projet Sirene

Pour qu'une application envoie une notification à Sirene, elle doit utiliser une petite bibliothèque commune. Toute la question est : comment la distribuer ?

  • Copier une DLL dans chaque projet est rapide, mais on perd vite la trace de la version utilisée par chaque application.
  • Publier un paquet NuGet, sur un flux privé à l'entreprise, permet de versionner la bibliothèque, de voir qui utilise quelle version et de mettre à jour proprement.

Ce que j'en retiens : NuGet est la bonne cible, mais l'entreprise prévoit d'y passer pour tous ses frameworks internes en même temps. Le choix retenu est donc une DLL simple pour l'instant, documentée comme dette technique : faire le travail deux fois aurait coûté plus cher que d'attendre.
